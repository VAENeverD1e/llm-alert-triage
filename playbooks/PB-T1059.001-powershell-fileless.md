# Playbook - T1059.001: PowerShell Fileless Execution

| Field          | Value                                              |
|----------------|----------------------------------------------------|
| Technique      | T1059.001 - Command and Scripting: PowerShell      |
| Severity       | High                                               |
| Detection rule | `Encoded PowerShell Execution Detection`           |
| Primary signal | Sysmon Event ID 1 (process creation)               |
| MITRE tactic   | Execution (TA0002)                                 |

---

## What triggered this alert

PowerShell was launched with flags or function calls commonly used to
decode and execute obfuscated content: `-enc`, `-encodedCommand`,
`FromBase64String`, `IEX`, or `Invoke-Expression`. These are fileless
execution indicators - the payload runs entirely in memory without
being written to disk first.

---

## Triage steps

**Step 1 - Identify the process**

In Kibana, pivot to the alert and inspect the following fields:

```
process.command_line    ← full PowerShell command
process.parent.name     ← what spawned powershell.exe?
process.parent.command_line
host.name               ← which endpoint?
user.name               ← which account?
@timestamp
```

**Step 2 - Decode the payload**

If `FromBase64String` or `-enc` is present, extract the base64 blob
from `process.command_line` and decode it:

```powershell
# On an isolated analysis machine only
# Try UTF-16LE first (default PowerShell encoding)
[System.Text.Encoding]::Unicode.GetString(
  [System.Convert]::FromBase64String("<paste_blob_here>")
)

# If the output contains null bytes or garbage, try UTF-8 instead
[System.Text.Encoding]::UTF8.GetString(
  [System.Convert]::FromBase64String("<paste_blob_here>")
)
```

Read the decoded string. Does it download a remote file, spawn a
child process, or modify the registry?

**Step 3 - Check the parent process**

| Parent process              | Interpretation                                      |
|-----------------------------|-----------------------------------------------------|
| `explorer.exe`              | User-initiated - investigate user context           |
| `winword.exe` / `excel.exe` | Macro execution - likely phishing                   |
| `cmd.exe`                   | Script or batch file execution                      |
| `svchost.exe`               | Scheduled task or service - check Task Scheduler    |
| `wscript.exe` / `mshta.exe` | LOLBin chain - high suspicion                       |

**Step 4 - Check for subsequent activity**

Search for child processes, network connections, and registry writes
within ±5 minutes of the alert timestamp on the same host:

```kql
host.name: "<hostname>" AND
@timestamp: [<alert_time - 5m> TO <alert_time + 5m>] AND
event.code: (1 OR 3 OR 13)
```

**Step 5 - Check for the Atomic Red Team marker (lab environment)**

If the decoded payload references `art-marker.txt` or
`mssharepointclient` registry key, this is a known Atomic Red Team
test (T1059.001 Test #10/11). Confirm with the operator before
treating as a production incident.

## TP vs FP escalation criteria

**Treat as TRUE POSITIVE if any of the following:**

- Decoded payload contacts an external IP or downloads a file
- Parent process is an Office application (macro execution)
- The executing user account is not an administrator and has no
  legitimate reason to run encoded PowerShell
- Subsequent Sysmon ID 3 shows outbound connection to non-standard port
- Registry write to `CurrentVersion\Run` follows within the same session

**Treat as FALSE POSITIVE if all of the following:**

- Parent is a known management tool (SCCM, Ansible, IT automation)
- The user is a system administrator with documented need
- Decoded payload matches known-good software deployment script
- No subsequent suspicious process creation or network activity

**Escalate immediately if:**

- Decoded payload contains `IEX (New-Object Net.WebClient).Download`
  (classic cradle) - potential active intrusion
- Multiple hosts show the same encoded command in a short window
  (lateral movement or worm behavior)

---

## Containment and response actions

**For confirmed TRUE POSITIVE:**

1. **Isolate the host** from the network (disable NIC or quarantine
   via EDR) to prevent lateral movement or C2 callback.

2. **Preserve evidence** before any remediation:
   - Export the full Sysmon Event ID 1 record from Elastic
   - Capture process memory if the PowerShell process is still running:

     ```powershell
     # Run on the affected host as Administrator
     procdump.exe -ma powershell.exe powershell.dmp
     ```

   - Export prefetch files: `C:\Windows\Prefetch\POWERSHELL*.pf`

3. **Kill the PowerShell process** if still running:

   ```powershell
   Stop-Process -Name powershell -Force
   ```

4. **Search for persistence artifacts** immediately after isolation:
   - Registry Run keys (`HKCU\...\CurrentVersion\Run`)
   - Scheduled tasks (`schtasks /query /fo LIST /v`)
   - Startup folder: `%APPDATA%\Microsoft\Windows\Start Menu\Programs\Startup`

5. **Reset credentials** for the affected user account.

6. **Re-image or restore from snapshot** if payload execution is
   confirmed. Do not trust the host without a clean baseline.

**For lab environment (Atomic Red Team):**

```powershell
Invoke-AtomicTest T1059.001 -TestNumbers 10 -Cleanup
# Verify marker file is removed:
Test-Path "C:\Windows\Temp\art-marker.txt"  # should return False
```
