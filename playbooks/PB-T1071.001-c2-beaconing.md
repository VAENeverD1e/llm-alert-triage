# Playbook - T1071.001: C2 Beaconing via Malicious HTTP User Agents

| Field            | Value                                                    |
|------------------|----------------------------------------------------------|
| Technique        | T1071.001 - Application Layer Protocol: Web Protocols    |
| Severity         | High                                                     |
| Detection rules  | `Malicious HTTP User Agent (C2 Beaconing)`               |
|                  | `Suspicious Script-Based Outbound Network Connection`    |
| Primary signal   | Suricata HTTP flow / alert                               |
| Secondary signal | Sysmon Event ID 3 (NetworkConnect)                       |
| MITRE tactic     | Command and Control (TA0011)                             |

---

## What triggered this alert

One of two rules may fire for this technique:

**Rule 1 - Malicious HTTP User Agent:** Suricata detected HTTP traffic
using a known-malicious user agent string associated with APT malware
families (HttpBrowser/1.0, Wget/1.9+cvs, Opera/8.81, `*<|>*`), or
matched a Suricata category for network trojans or malware C2.

**Rule 2 - Suspicious Script Egress:** Sysmon Event ID 3 detected an
outbound connection from `powershell.exe`, `cmd.exe`, or `wscript.exe`
to a commonly abused C2 port (4444, 8080, 8888, 1337).

Unlike network scanning (T1046), C2 beaconing means the host is
**already compromised** and actively communicating with an attacker.
This is the highest-priority alert category.

---

## Triage steps

**Step 1 - Identify the beaconing host and C2 destination**

For Rule 1 (Suricata), inspect:

```
source.ip                           ← the compromised host
destination.ip                      ← C2 server IP
destination.port                    ← C2 port
user_agent.original                 ← the malicious user agent string
suricata.eve.http.http_method       ← HTTP method (usually GET)
rule.name                           ← specific signature matched
@timestamp
```

For Rule 2 (Sysmon ID 3), inspect:

```
process.name            ← powershell.exe / cmd.exe / wscript.exe
process.command_line    ← what was the script doing?
destination.ip
destination.port
network.direction       ← should be egress
host.name
user.name
@timestamp
```

**Step 2 - Classify the C2 destination**

Is the destination IP internal or external?

- **Internal IP** - likely lab simulation, authorized red team, or
  misconfigured tool. Lower urgency but still investigate.
- **External IP** - active C2 callback. Escalate immediately.
  Look up the IP in threat intel (VirusTotal, Shodan, AbuseIPDB).

**Step 3 - Identify the beaconing process**

Correlate the Suricata network alert with the Sysmon endpoint event
to get process-level attribution:

```kql
host.name: "<source_hostname>" AND
event.code: 3 AND
@timestamp: [<alert_time - 30s> TO <alert_time + 30s>]
```

> **Note:** In Sysmon Event ID 3, the local endpoint address maps to
> `source.ip`, not `host.ip`. Prefer `host.name` for the endpoint
> pivot; use `source.ip: "<source_ip>"` only if you need to filter
> on the specific interface address.

This gives you `process.name`, `process.pid`, and `process.command_line`
for the process that made the connection.

**Step 4 - Analyze the beaconing pattern**

Use Kibana Lens to visualize connection frequency over time:

- **Periodic, regular interval** (e.g. every 60s) → classic beacon
  with fixed sleep timer - high confidence C2
- **Single burst of rapid requests** → automated tool execution
  (possibly Atomic Red Team or script)
- **Irregular, infrequent** → interactive C2 session (attacker
  actively working the shell)

**Step 5 - Check the process tree**

What launched the beaconing process?

```kql
host.name: "<hostname>" AND
event.code: 1 AND
process.name: "<beaconing_process>" AND
@timestamp: [<alert_time - 10m> TO <alert_time>]
```

Common infection chains:

- `winword.exe` → `powershell.exe` → beacon (macro-based initial access)
- `explorer.exe` → `powershell.exe` → beacon (user executed dropper)
- `svchost.exe` → `powershell.exe` → beacon (scheduled task or service)

**Step 6 - Check for malicious user agent in full HTTP payload**

If Suricata logged HTTP metadata, extract the full request for context:

```kql
event.module: suricata AND
suricata.eve.event_type: http AND
source.ip: "<source_ip>" AND
@timestamp: [<alert_time - 5m> TO <alert_time + 5m>]
```

Fields of interest: `http.request.method`, `http.request.body.content`,
`http.response.status_code`, `url.original`.

## TP vs FP escalation criteria

**Treat as TRUE POSITIVE if any of the following:**

- User agent exactly matches a known APT malware string
  (HttpBrowser/1.0, Wget/1.9+cvs-stable, `*<|>*`)
- Destination IP is external and flagged in threat intel
- Traffic is periodic/regular (classic beacon interval)
- The beaconing process is spawned from a browser, email client,
  or document application
- Suricata fires a category alert: "A Network Trojan was detected"

**Treat as FALSE POSITIVE if all of the following:**

- Destination is an internal IP (lab/test environment)
- The source is a known red team or pen test host
- The user agent matches a legitimate automation tool in your
  authorized tool inventory
- Traffic is a one-time burst with no recurrence

**Escalate immediately if:**

- Destination IP is external and the host is a production server
- The beacon has been running for more than a few minutes
  (attacker may already have interactive access)
- Lateral movement events appear on other hosts after the first beacon
- The beaconing process is `SYSTEM`-level (high privilege C2)

---

## Containment and response actions

**For confirmed TRUE POSITIVE:**

1. **Isolate the host immediately** - cut network access to prevent
   further C2 communication and lateral movement. Time is critical:
   every beacon cycle may deliver new attacker commands.

2. **Block the C2 destination** at the perimeter firewall and proxy:
   - IP-based block for the C2 server IP
   - DNS sinkhole for the C2 domain (if domain-based)

3. **Preserve memory** before killing the beaconing process - the
   C2 implant may exist only in memory:

   ```powershell
   # Run on an isolated forensic copy if possible
   procdump.exe -ma <beaconing_process_PID> "\\forensic-share\<case_id>\beacon_memory.dmp"
   ```

4. **Kill the beaconing process:**

   ```powershell
   Stop-Process -Id <PID> -Force
   ```

5. **Identify and remove the implant:**
   - Locate the file that launched the beacon (from the process tree)
   - Preserve a copy, then delete
   - Check for persistence mechanisms that would re-launch it

6. **Search for lateral movement** from the compromised host:

   ```kql
   source.ip: "<compromised_ip>" AND
   event.code: (4624 OR 4648) AND
   winlog.event_data.LogonType: (3 OR 10)
   ```

7. **Hunt for additional compromised hosts** using the same C2 IP/domain:

   ```kql
   destination.ip: "<c2_ip>" AND
   event.module: suricata
   ```

8. **Reset all credentials** on the compromised host (same reasoning
   as T1003.001 - assume credential access occurred during dwell time).

**For lab environment (Atomic Red Team):**

```bash
# On ELK server - stop the Python HTTP listener that served as C2:
kill $(lsof -t -i:8080)
```

## Evidence collection checklist

- [ ] Suricata alert - `source.ip`, `destination.ip`, `user_agent.original`
- [ ] Suricata HTTP flow - full request metadata
- [ ] Sysmon Event ID 3 - process name, PID, destination IP/port
- [ ] Process command line of the beaconing process
- [ ] Parent process chain (full process tree)
- [ ] Beacon frequency/pattern (Kibana time histogram screenshot)
- [ ] Threat intel lookup result for destination IP/domain
- [ ] `user.name` and `host.name`
- [ ] `@timestamp` range of beacon activity
- [ ] Memory dump of beaconing process (if captured)
- [ ] Any files written or downloaded during the beacon session
- [ ] Lateral movement events from the compromised host
